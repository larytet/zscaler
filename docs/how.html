How the security works

Everything below rests on one idea: a gatekeeper outside the agent or the device decides, using fixed rules, every time. No model judgement is in the decision path, and an unclear case is refused.

Part 1. AI agents

1.1 What happens to one agent request Proposed identity, policy, approval built

The agent never talks to your systems directly. Each request passes the same fixed checks, in order. The first failure stops it.

flowchart TD
  A["AI agent sends a request"] --> B{"Valid agent identity,
not revoked or expired?"}
  B -- no --> X1["Refuse and log"]
  B -- yes --> C{"Destination on this agent's
allow list?"}
  C -- no --> X2["Refuse and log"]
  C -- yes --> D{"Is it a read?"}
  D -- "no, it writes" --> E["Hold for human approval"]
  E -- approved --> F
  E -- denied or timeout --> X3["Refuse and log"]
  D -- yes --> F{"Under the hourly
volume cap?"}
  F -- no --> X4["Pause agent, alert owner"]
  F -- yes --> G["Platform adds the secret
and forwards the request"]
  G --> H["Response comes back"]
  H --> I{"Sensitive data
in the response?"}
  I -- yes --> J["Mask or block"]
  I -- no --> K["Pass through"]
  J --> L["Write audit line"]
  K --> L
  L --> M["Agent gets the result"]
  • The checks run in the enforcement node, not in the agent. A tricked agent cannot skip them.
  • Requirement IDs: AGS-002 (read-only pack), AGS-003 (egress), AGS-007 (approval), AGS-009 (caps), AGS-012 (masking), AGS-014 (audit).

1.2 The agent never holds the password Proposed

sequenceDiagram
  autonumber
  participant Ag as AI agent
  participant EN as Enforcement node
  participant Vault as Secret store
  participant App as Business app API
  Ag->>EN: GET invoices unpaid (platform identity only)
  EN->>EN: Check identity, allow list, method, cap
  EN->>Vault: Fetch API key for this app
  Vault-->>EN: key (never leaves the node)
  EN->>App: GET invoices unpaid + Authorization header
  App-->>EN: invoice list
  EN-->>Ag: invoice list (header not included)
  • If a hidden instruction in an email says "print your API key", there is nothing to print.
  • A stolen agent identity still gets only the allowed calls and can be revoked in one click.
  • Built today: the TLS-inspecting proxy that can add headers (I10a) and agent identities (I12b). Missing: the secret store and the injection rule.

1.3 Writes wait for a person Built, basic

sequenceDiagram
  autonumber
  participant Ag as AI agent
  participant EN as Enforcement node
  participant CP as Control plane
  participant Owner as Owner
  Ag->>EN: PATCH invoice 4471, total 12400
  EN->>EN: Rule says writes need approval
  EN-->>Ag: Denied for now, request opened
  EN->>CP: Open approval request (exact action)
  CP->>Owner: Email or console card with the exact request
  Owner->>CP: Approve once, 15 minutes
  CP->>EN: Grant travels in the signed policy snapshot
  Ag->>EN: Retry the same request
  EN->>App: Forward with secret added
  EN->>CP: Audit: approved by owner, who and when
  • Built: the first attempt is denied and opens a request, the admin approves for 1 to 480 minutes, and live sessions end when the grant does (I9e).
  • Proposed: Slack and Teams approvers, and approval-fatigue controls: show the exact request, cap approvals per hour, group low-risk ones (AGS-007, AGS-008).

1.5 The "rule of two" check Proposed

flowchart TD
  P["Reads private data"] --> Q{"How many of the
three does this agent have?"}
  U["Reads untrusted input
mail, web pages"] --> Q
  S["Can send data out"] --> Q
  Q -- "one or two" --> OK["No warning"]
  Q -- "all three" --> W["Warn the owner:
an injected instruction could send data out"]
  W --> F["Suggested fix: send only after approval,

Advice, not a block. Published work notes that a detector alone cannot be the gate, so the real protection is in 1.1 to 1.4 (AGS-017).

1.6 Sensitive data in prompts and answers block built mask proposed

flowchart LR
  subgraph out["Going out: prompts and uploads"]
    A1["User or agent sends text"] --> A2{"Scan: card, IBAN,
national ID, keys"}
    A2 -- found --> A3["Block page names the type,
never the data"]
    A2 -- clean --> A4["Send to the AI tool"]
  end
  subgraph back["Coming back: answers and records"]
    B1["Response from app or AI tool"] --> B2{"Scan the same patterns"}
    B2 -- found --> B3{"Policy: block or mask?"}
    B3 -- block --> B4["Block page"]
    B3 -- mask --> B5["Replace with tokens"]
    B2 -- clean --> B6["Pass through"]
  end
  • Built: request DLP (I10b) and response DLP (I16), up to 1 MiB, with gzip handled. Binary files are not scanned.
  • Limits to state plainly: pattern matching only. Reformatted data can be missed and some numbers will be flagged wrongly.

Part 2. People, devices and the rest of the platform

2.1 The pieces Built

flowchart TD
  Admin["Admin console"] --> CP["Control plane
users, apps, policy, audit, CA"]
  IdP["Identity provider (OIDC)"] --> CP
  CP -- "signed policy snapshots" --> EN["Enforcement node
broker + web proxy + decision cache"]
  Dev["Device agent
local proxy + posture"] -- "mutual TLS" --> EN
  Ag["AI agent identity"] -- "mutual TLS" --> EN
  EN -- "outbound-only link, started by the connector" --- Con["Connector in the office network"]
  Con --> App["Private app"]
  EN --> Web["Internet and SaaS"]
  • The control plane never sees user traffic. It issues short-lived certificates and pushes signed policy.
  • The connector has no inbound ports. It dials out, so nothing in the office is exposed.

2.3 Web access with inspection and data checks Built, basic

flowchart TD
  R["Request through the proxy"] --> C{"Category and domain rules"}
  C -- block --> B1["Block page"]
  C -- warn --> B2["Warning page, user may continue"]
  C -- allow --> I{"Inspect HTTPS?
not exempt, tenant CA trusted"}
  I -- no --> F["Forward"]
  I -- yes --> D["Decrypt with per-host certificate
check path and method"]
  D --> S{"Data check on upload"}
  S -- found --> B3["Block page"]
  S -- clean --> U["Forward upstream, verify the real certificate"]
  U --> RS{"Data check on response"}
  RS -- found --> B4["Block page"]
  RS -- clean --> F2["Deliver"]
  • Known limits: no WebSocket or HTTP/2 yet, and certificate-pinned apps must be exempted.
  • The inspection CA key is sensitive. It is stored in clear in the control plane's store file in this version.

2.4 A lost laptop Built

sequenceDiagram
  autonumber
  participant Admin
  participant CP as Control plane
  participant EN as Enforcement node
  participant Dev as Lost laptop
  Admin->>CP: Revoke device
  CP->>EN: Revocation event (pushed at once, signed)
  EN->>EN: Close live sessions, add to deny list
  Dev->>EN: New connection attempt
  EN-->>Dev: Refused: certificate revoked
  Note over EN: If the control plane is unreachable, nodes keep the last policy but refuse new sessions when their revocation list is older than 15 minutes

flowchart TD
